## 1. P0. Исправить основную ошибку продукта: показывать развитие ВСЕХ направлений, а не один main

Текущее `GithubClient.load()` делает `/commits?sha=<default_branch>&per_page=12`. Такой набор **не является всей историей UNO**. Загружай полный доступный список веток с пагинацией и отдельно сохраняй его полноту. При повторном успешном обновлении сравни `name + HEAD SHA` текущего и предыдущего полных снимков; отобрази изменившиеся направления. Если HEAD ветки изменился, получи необходимые детали этого изменения по запросу, без автоматических утверждений об успешной реализации. Дай пользователю возможность открыть выбранную ветку и её историю, в том числе `research/*`. Общий обзор не должен называть последний коммит `main` последним событием всего проекта.

На первой синхронизации при `previous = null` нельзя сообщать «изменений нет», «новых веток нет» или «проект не развивается»: **нет базы сравнения**. Неполный список веток, импорт JSON и сетевые ошибки никогда не должны порождать ложные выводы о новых/исчезнувших ветках. Когда SHA не изменились, но изменились Issues/PR, показывай именно события задач. Отдельно обозначай покрытие: «полностью проверены указатели веток», «история изучена лишь частично».

Не делай по 20-100 запросов на каждый запуск без нужды. Используй ограниченную очередь, кеш и загрузку подробностей по требованию. Учитывай 403/429 и отмену запросов. Никаких заявлений «проанализированы все коммиты», если это не подтверждено.

**Приёмка:** фикстура с изменением исследовательской ветки при неизменном `main` отображает событие; фикстура `previous=null` не выводит сравнение; неполная пагинация не выдаётся за полноту; изменения Issue/PR не теряются при равных SHA.

## 2. P0. Реальная работа с GitHub API и разрешениями

Исправь `GithubClient` и сообщения ошибок:

- `401`: токен недействителен/истёк. `404`: проект не найден **или** нет доступа. `403`: недостаточно прав, ограничение доступа к endpoint, лимит запросов или политика GitHub, а не автоматически «неправильный токен». `429`/rate limit: уважать `X-RateLimit-Remaining`, `X-RateLimit-Reset`, `Retry-After`, сообщение API. Сырой `Read timed out` не показывать пользователю.
- Раздели состояние каждого источника: ветки, история коммитов, Issues, PR, файлы, CI. Ошибка части API не превращается в «0 задач» и не стирает последний удачный снимок. Покажи дату последней удачной загрузки и причину неполноты простыми словами.
- Для деталей используйте `GET /issues/{number}`, `GET /pulls/{number}`, `GET /pulls/{number}/files`, `GET /commits/{sha}` с правильной пагинацией и отметкой неполного списка файлов. Состояния `PR closed` и `PR merged` различать по `merged`/`merged_at`, не только по `state`.
- Для проверок `GET /commits/{sha}/check-runs` НЕ рассчитывай, что обычный fine-grained PAT может читать Checks приватного репозитория. GitHub документирует для этого endpoint токены GitHub App с `Checks: read`. Сделай безопасный fallback: `GET /commits/{sha}/status` (разрешение `Commit statuses: read`), при необходимости `GET /actions/runs` (`Actions: read`) с привязкой результата к точному SHA. Если источников нет, напиши «Результаты автоматических проверок недоступны». Не объявляй отсутствие доступных тестов успехом. Не предлагай пользователю токен с правом записи. GitHub App — отдельная будущая задача, не вводи новый сервер без разрешения.
- Различай `success`, `failure`, `pending`, `cancelled`, `timed_out`, `skipped`, `neutral`, отсутствие статусов и частично прочитанный ответ. `skipped` и `neutral` НЕ являются «всё успешно».
- Нормальные тайм-ауты, ограниченный повтор безопасных GET-запросов, отмена, backoff, понятный экран повторной попытки. При 429 не повторяй запрос до разрешённого времени.

**Приёмка:** фикстуры 401/403 permission/403 rate-limit/404/429/timeout, частичная пагинация и отсутствие Checks дают корректный русский текст, сохраняют старые данные и не портят статус токена. Отдельный тест для fallback commit statuses и отсутствия CI.

## 3. P0. Главный экран для человека, не для программиста

На первом экране ровно одна понятная сводка с тремя смысловыми частями:

**Что изменилось:** например, «В исследовательской ветке появились новые изменения. Их работоспособность не проверена». Если доказанных событий нет — честно сообщить, с чем и что сравнили.

**Что требует внимания:** одна-две конкретные открытые проблемы с ссылкой на источник, либо «Не удалось получить сведения о проверках»; не придумывать очередные задачи.

**Следующий шаг:** действие, которое действительно может выполнить пользователь: «Открыть изменения», «Посмотреть задачу», «Повторить загрузку», «Проверить доступ».

Кнопка «Обновить» должна быть очевидной. Дата последнего успешного обновления и отметка «частичные данные» должны быть видны без прокрутки. На главной НЕ показывать английские коммиты, SHA, сырые даты, JSON и длинные общие предупреждения. Все технические сведения перенести в «Технические детали».

**Приёмка:** на экране A52 обычный пользователь за 10 секунд может ответить, что нового, что неизвестно и куда нажать дальше. Слова `SHA`, `HEAD`, `merge`, `check-run` не требуются для понимания главного экрана.

## 4. P0. Отдельные полноценные экраны, а не большие диалоги

Сохрани нативную навигацию и исправь UX в `SectionActivity`:

- «Обзор», «Направления работы», «История изменений», «Задачи», «Предложения изменений», «Надёжность сведений», «Подключение GitHub», «Настройки» — отдельные полноэкранные разделы с правильным заголовком.
- Системный Back и стрелка «Назад» возвращают на предыдущую страницу, не перезапускают приложение и не теряют текущий проект. Прокрутка, поворот/пересоздание Activity, светлая/тёмная темы не ломают экран.
- Каждый элемент списка открывает собственную страницу понятных подробностей: **суть изменения → подтверждения → неопределённость → источник**. Оригинальный заголовок, SHA, UTC, путь файла доступны во вторичном блоке «Технические детали» (с копированием), не наверху.
- Даты для пользователя форматировать по локали и времени устройства. Длинные названия должны переноситься аккуратно. Не показывать огромные однотипные карточки из одного сырого поля API.
- Ветка — направление работы, не доказательство результата. Подписи по префиксу `research/`, `feat/`, `docs/` обозначать как **предположение по названию**, а не установленный факт.

**Приёмка:** запись экрана/скриншоты главного экрана, списка направлений, истории, задач, подробности коммита, окна ошибки и светлой темы; проверка аппаратного Back на каждом экране. Не заявлять DEVICE_VERIFIED без устройства.

## 5. P0. Проверяемые объяснения: источник, степень уверенности, отсутствие выдумок

`HumanReport.commitSummary()` сейчас классифицирует записи по `docs:`, `fix:`, `feat:`. Это **эвристика названия**, не анализ кода. Для каждой карточки раздели:

1. **Что заявил автор** — исходное сообщение коммита/Issue/PR.
2. **Что подтверждает GitHub** — ветка, точный SHA, список файлов, состояние PR, доступные результаты checks/statuses.
3. **Чего установить нельзя** — фактическую работоспособность, закрытие всех требований, испытания A52, если доказательств нет.

Пример для `docs(agents): restore canonical work log route [skip ci]`: «Изменены инструкции/документация для работы разработчиков; в коммите затронуты AGENTS.md и README.md. Это не доказательство готовности UNO». Такой вывод допустим только если список файлов реально получен; без списка файлов сформулировать осторожнее.

`[skip ci]` — часть текста коммита, НЕ успешная проверка. Не переводить `closed` как «сделано». Не придумывать новые факты, процент готовности или рекомендации из одних названий. Если доказательств недостаточно — «Недостаточно данных» + какой именно источник не получен.

**Приёмка:** минимум 8 тестов против ложных утверждений (только заголовок, нет файлов, `skipped`, `neutral`, закрытый несмерженный PR, настоящий merge, неполная страница, отсутствующие тесты).

## 6. P0. Безопасность и сохранность данных

Сохрани `TokenVault`: Android Keystore, AES-GCM, отдельный токен на `owner/repo`, `noBackupFilesDir`, `allowBackup=false`, отсутствие PAT в экспортируемом JSON, логах, скриншотах и debug-артефактах. Пустое поле ввода не удаляет токен; удаление затрагивает только выбранный проект. Не отправляй реальный PAT исполнителям, не используй его в тестовых фикстурах.

Синхронизация не имеет права менять результат при смене репозитория или возврате назад: старые callbacks не перезаписывают новый проект; старый успешный снимок сохраняется после timeout/403/429. Доступ GitHub строго read-only (`GET`), без записи в чужие репозитории.

**Приёмка:** сохранение после перезапуска, разные токены на два проекта, повреждённый контейнер, обновление после `force-stop`, импорт/экспорт без секретов, смена проекта во время запроса. Проверку очистки данных проводить только на отдельном тестовом окружении, не на пользовательском A52.

**Порог готовности:** только если пользователю понятны актуальные изменения, видны источники и ограничения, а доступность API корректно обработана. Успешная сборка не означает готовность к продаже; `NOT_DEVICE_VERIFIED` до испытания на физическом устройстве.
